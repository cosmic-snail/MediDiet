# MediDiet 微信小程序原型使用文档

本文档用于说明 MediDiet 推荐引擎微信小程序前端原型的启动方式、三类角色的演示路径，以及后续与推荐引擎接口对接时需要关注的数据概念。

前端端到端功能验证和大模型辅助验收见：

- `../../docs/frontend-e2e-llm-verification.zh.md`
- `../../docs/frontend-e2e-test-results-2026-05-19.zh.md`

## 1. 原型定位

本原型是一个面向微信小程序落地的移动端浏览器原型，用来验证同一个小程序中三类角色的入口与核心工作流：

- 患者：查看健康资料、补录摄入、发起下一餐推荐、查看推荐/拒绝/等待审核结果。
- 营养师：作为医疗审核人员处理待审核推荐，查看 Trace 证据链并做确认、修改或驳回。
- 配餐管理人员：维护菜单可售状态、营养信息、数据质量和轻量履约状态。

当前实现为本地 React/Vite 原型，不依赖真实微信小程序运行时、后端 HTTP 服务、图片识别、支付或生产级临床规则。

## 2. 快速启动

在仓库根目录进入原型目录：

```bash
cd apps/mini-program-prototype
```

安装依赖：

```bash
npm install
```

启动后端 HTTP 服务。在仓库根目录打开一个终端：

```bash
uvicorn medidiet.server:app --app-dir src --reload
```

默认后端地址：

```text
http://127.0.0.1:8000
```

启动前端本地预览。另开一个终端进入原型目录：

```bash
npm run dev -- --host 127.0.0.1
```

浏览器打开：

```text
http://127.0.0.1:5173/
```

前端开发服务会把 `/api/*` 代理到 `http://127.0.0.1:8000/*`。如需改后端地址，可设置：

```bash
VITE_MEDIDIET_API_BASE_URL=http://127.0.0.1:8000 npm run dev -- --host 127.0.0.1
```

运行测试：

```bash
npm run test
```

构建检查：

```bash
npm run build
```

## 3. 页面结构

进入页面后，顶部是统一的“角色工作台”。三类角色通过同一个角色切换入口进入：

- 患者
- 营养师
- 配餐

角色切换仅用于原型演示。真实微信小程序落地时，应由登录态、机构身份、患者绑定关系和权限策略决定可见入口。

## 4. 患者端使用路径

默认进入患者工作台。

### 4.1 查看今日概览

页面顶部会展示：

- 今日摄入数量
- 当前推荐状态

这部分用于快速告诉患者：系统已经记录了多少摄入信息，以及是否已有一条可展示的推荐结果。

### 4.2 切换患者身份并查看健康资料

患者工作台提供本地原型身份切换入口。当前原型内置两位演示患者，用于验证同一个患者端页面在不同患者资料下的展示和推荐联动。

切换患者后，页面会同步更新：

- 今日概览中的摄入数量和推荐状态。
- 健康资料卡片中的疾病、过敏、口味偏好、预算范围和关键风险确认状态。
- 今日摄入列表。
- 下一餐推荐结果。

这仍然只是本地原型身份切换，用于演示患者资料、摄入记录和推荐结果之间的前端联动；它不代表真实登录、认证、授权、家庭成员绑定或机构患者关系管理。后续对接真实接口时，这部分应来自 `PatientProfile`，并由登录态、绑定关系和权限策略决定当前可访问患者。

### 4.3 补录摄入

“今日摄入”卡片展示已有摄入记录。点击“手动补录低糖酸奶”后，会新增一条患者手动补录的摄入记录。

原型中补录按钮是固定示例，用于验证患者手动修正入口。后续真实实现可以扩展为：

- 拍照识别
- 手动搜索食物
- 份量选择
- 营养估算结果确认
- 患者修正记录

后续对接真实接口时，这部分应映射到 `IntakeRecord`。

### 4.4 查看推荐结果

推荐结果可能出现三类状态：

- 已生成推荐：展示推荐餐食、患者解释、营养标签和 trace id。
- 拒绝推荐：展示暂不推荐原因。
- 等待营养师审核：说明当前推荐需要医疗审核人员确认。

原型中可点击：

- “获取下一餐推荐”：回到正常推荐结果。
- “模拟拒绝推荐”：演示推荐引擎拒绝自动推荐的状态。
- “模拟等待营养师审核”：演示进入营养师审核队列的状态。

当前点击“获取下一餐推荐”会先读取 `GET /debug/state`，再把当前患者、当前患者的摄入记录和推荐候选菜单写入后端内存服务，最后调用 `POST /recommendations` 获取真实推荐结果。为避免把配餐端的“数据待补”样例误送入推荐，前端只会向后端提交可售且营养置信度不低于 `0.7` 的菜单项。后端未启动或返回错误时，页面会保留当前推荐结果，并显示后端错误信息。

后续对接真实接口时，这部分应来自 `RecommendationResult` 和 `RecommendationTrace`。

## 5. 营养师端使用路径

点击顶部“营养师”进入审核工作台。

### 5.1 查看待审核队列

页面展示当前待审核数量、患者姓名、餐次、风险等级、待审原因和 trace id。

如果没有待审核推荐，会展示“暂无待审核推荐”，并隐藏审核动作。

### 5.2 查看 Trace 证据链

Trace 证据链用于辅助营养师判断推荐是否可以放行。当前原型展示：

- Outcome
- Risk
- Safety
- Rule
- Exclusions
- Scores
- 排除项
- 评分
- 命中标签
- 患者解释
- LLM 边界说明

后续对接真实接口时，这部分应尽量直接消费 `RecommendationTrace.to_dict()` 或等价 JSON 输出，避免前端重新推导规则判断。

### 5.3 提交审核动作

当前支持三个动作：

- 确认推荐
- 修改推荐
- 驳回推荐

提交后，待审核队列会更新；同时患者侧可见结果会被同步写回：

- 确认推荐：患者侧展示“清蒸鱼套餐”和营养师确认后的解释文案。
- 修改推荐：患者侧展示调整后的推荐解释。
- 驳回推荐：患者侧展示“需要处理”和营养师未通过的原因。

这个闭环用于验证“营养师审核结果必须回写患者端”的产品要求。

## 6. 配餐管理端使用路径

点击顶部“配餐”进入配餐管理工作台。

### 6.1 查看菜单列表

菜单列表展示：

- 菜品名称
- 价格
- 营养置信度
- 营养标签
- 可售/下架状态

点击“下架清蒸鱼套餐”后，第一条菜品会变为下架状态。该交互用于演示推荐候选池与配餐可售状态之间的关系。

### 6.2 查看营养详情

营养详情展示主要营养字段：

- 能量
- 碳水
- 蛋白质
- 钠

后续对接真实接口时，这部分应来自 `MenuItem.nutrients`，并保留数据来源与置信度字段，方便营养师或运营人员判断数据可靠性。

### 6.3 处理轻量履约

“已确认餐食”区域展示待准备的餐食。点击“标记已备餐”后，状态会变为“已备餐”。

当前只是轻量演示。真实落地时可以扩展为：

- 待接单
- 备餐中
- 已备餐
- 已取餐/已送达
- 取消
- 异常反馈

## 7. 数据与接口对接说明

原型中的接口概念集中在以下文件：

- `src/contracts.ts`：前端 DTO 类型定义。
- `src/fixtures.ts`：演示用数据。
- `src/state.ts`：本地状态机，用于模拟接口返回和角色间流转。
- `src/api/adapters.ts`：前后端 DTO 转换。
- `src/api/medidietApi.ts`：HTTP 请求封装。

重要数据概念：

- `PatientProfile`：患者画像、疾病、过敏、偏好、预算和风险确认状态。
- `IntakeRecord`：患者摄入记录，包括餐次、份量、营养估算、置信度和来源。
- `MenuItem`：菜单菜品，包括营养值、标签、禁忌、价格、距离、可售状态和数据来源。
- `RecommendationResult`：推荐结果，包括 outcome、riskLevel、recommendedItems、patientExplanation、reviewStatus 和 traceId。
- `RecommendationTrace`：推荐证据链，包括 safetyEvents、exclusions、scores、clinicianExplanation 等。
- `ReviewCase`：营养师审核队列项。
- `Fulfillment`：配餐履约状态。

建议后续接口分层：

- 患者端读取 `PatientProfile`、`IntakeRecord`、`RecommendationResult`。
- 营养师端读取 `ReviewCase` 和完整 `RecommendationTrace`。
- 配餐端读取和更新 `MenuItem`、`Fulfillment`。
- 推荐接口只返回结构化结果，前端只负责展示、确认和提交动作，不在前端重算临床规则。

当前已接入的后端接口：

- `GET /debug/state`
- `PUT /patients/{patient_id}`
- `POST /patients/{patient_id}/intake-records`
- `PUT /menus/today`
- `POST /recommendations`

当前 HTTP 适配层会保持以下边界：

- 患者资料和当日菜单使用幂等写入，便于重复演示。
- 摄入记录只在后端还没有该患者记录时补写，避免重复点击推荐造成摄入记录叠加。
- 配餐端仍展示全部演示菜单；推荐请求只提交满足后端自动推荐条件的候选菜单。

当前仍保留本地原型状态的部分：

- 营养师审核队列
- 营养师确认、修改、驳回动作
- 配餐菜单维护和履约状态

## 8. 建议演示脚本

可以按下面顺序演示：

1. 进入患者工作台，查看健康资料、今日摄入和推荐结果。
2. 点击“手动补录低糖酸奶”，说明患者可修正摄入记录。
3. 点击“模拟等待营养师审核”，说明高风险或低置信度推荐进入审核。
4. 切换到“营养师”，查看待审核队列和 Trace 证据链。
5. 点击“确认推荐”，说明审核结果会写回患者侧。
6. 切回“患者”，确认患者看到营养师确认后的推荐结果。
7. 切换到“配餐”，查看菜单数据、下架菜品和标记已备餐。

如需演示驳回路径：

1. 刷新页面。
2. 直接进入“营养师”。
3. 点击“驳回推荐”。
4. 切回“患者”，确认页面显示“需要处理”和“拒绝推荐”。

## 9. 当前边界

本原型暂不包含：

- 微信小程序原生页面和组件。
- 登录、绑定患者、机构权限和真实角色授权。
- 真实登录、认证、授权或患者绑定 API。
- 图片识别或餐食搜索。
- 医嘱、禁忌和临床规则的真实计算。
- 支付、配送、取餐码。
- 多患者、多机构、多门店协作。

这些边界是刻意保留的，目的是先验证三类角色在同一个小程序中的信息架构、审核闭环和推荐证据链展示方式。
